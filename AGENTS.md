# Спільні інструкції для AI-агентів

Цей файл є єдиним джерелом стабільних правил для Claude Code, Codex, GitHub Copilot та інших AI-агентів, які працюють з репозиторієм.

## 1. Контекст

Проєкт — індивідуальний магістерський інженерний проєкт Neoversity, Software Engineering.

Робоча тема:

**«Оцінювання доступності критичних побутових сервісів під час відключень електроенергії на основі моделі функціональних залежностей»**.

Перед будь-якою суттєвою реалізацією прочитай відповідні канонічні документи в `docs/`.

## 2. Канонічні документи та поточний контекст

- `docs/STATUS.md` — короткий поточний operational snapshot: етап, активне завдання, ролі, open questions, остання фактична перевірка та next action.
- `docs/PROJECT.md` — проблема, користувач, мета, MVP, межі та поточний етап архітектури.
- `docs/DOMAIN_MODEL.md` — предметна модель, типи сутностей, зв’язки та інваріанти.
- `docs/SIMULATION.md` — правила симуляції, стани сервісів, bottleneck та причинний шлях.
- `docs/TEST_SCENARIOS.md` — контрольні сценарії й очікувані результати.
- `docs/DECISIONS.md` — історичний журнал лише суттєвих архітектурних, продуктових, алгоритмічних і технологічних рішень.
- `docs/specs/` — погоджені специфікації.
- `docs/plans/` — плани реалізації конкретних змін.

Поточна істина про поведінку системи міститься у відповідному канонічному документі, а не в `DECISIONS.md` і не в історії чату.

Якщо код або завдання суперечить канонічному документу, не виправляй суперечність мовчки. Зупинись і зафіксуй її для користувача.

## 3. Режим роботи задається в кожному завданні

Агент не має постійно закріпленої ролі. Claude Code, Codex і GitHub Copilot можуть по черзі працювати як `Developer` або `Reviewer`.

### Developer

- Реалізуй лише погоджене завдання.
- Не розширюй scope без явного рішення користувача.
- Не змінюй архітектурні рішення приховано.
- Змінюй тільки файли, потрібні для завдання.
- Для змін у предметній або алгоритмічній логіці додавай або оновлюй релевантні тести.
- Перед заявою про завершення виконай усі доступні перевірки, пов’язані зі зміною, і повідом фактичний результат.
- Якщо вимога неоднозначна або суперечить канонічній документації, не приймай нове суттєве рішення самостійно: застосуй synchronization protocol з розділу 12.

### Reviewer

- За замовчуванням не змінюй код.
- Перевіряй реалізацію відносно task/spec, канонічної документації та acceptance criteria.
- Перевіряй коректність логіки, scope, тести, архітектурні обмеження, читабельність і зайву складність.
- Розділяй findings щонайменше на `Critical`, `Major`, `Minor`.
- Не створюй нові вимоги під час review.
- Якщо виправлення потрібні, передай конкретні зауваження поточному `Developer`, якщо користувач явно не доручив перейти в режим `Developer`.

## 4. Правила scope

Пріоритет: просте, завершене, протестоване й вимірюване рішення.

Не додавай без конкретної вимоги:

- microservices;
- Kubernetes;
- CQRS;
- event-driven architecture;
- distributed-system complexity;
- складну cloud infrastructure;
- AI-функції;
- зовнішні інтеграції.

Кожен новий компонент повинен відповідати на питання: **яку конкретну вимогу або проблему він вирішує?**

## 5. Технологічні обмеження

Поточний погоджений напрям:

- React — перший етап реалізації;
- Node.js — можливе подальше розширення лише після появи конкретної серверної вимоги.

Не обирай самостійно нову БД, ORM, testing framework, message broker, cloud service або іншу допоміжну технологію.

Якщо для завдання потрібна ще не погоджена технологія, зупинись і запитай користувача:

**«Чи проходили ви цю технологію в межах навчальної програми?»**

Після погодження важливий вибір має бути зафіксований у `docs/DECISIONS.md` і, якщо потрібно, у відповідному канонічному документі.

## 6. Архітектурні правила

- Предметна та симуляційна логіка повинна залишатися відокремленою від UI.
- Не переносити бізнес-правила в React-компоненти лише для зручності.
- Не додавати backend тільки «для складності» або «для солідності».
- Якщо backend буде додано, він має вирішувати зафіксовану вимогу.
- Значні зміни архітектури спочатку документуються як рішення, потім реалізуються.

## 7. Тестування і перевірка

Підтримуй трасування:

`Requirement → Implementation → Test → Result`

Правила:

- acceptance criteria мають бути перевірюваними;
- результати тестів і benchmarks не вигадувати;
- якщо перевірка не запускалася, не стверджувати, що вона пройшла;
- негативні сценарії та валідація є частиною перевірки основної логіки;
- конкретний testing framework не вибирати без погодження.

## 8. Документація

Основна мова документації — українська.

Англійською залишаються:

- назви файлів;
- code identifiers;
- назви класів, типів, функцій, enum та API;
- усталені технічні терміни, коли переклад погіршує точність.

Не дублюй однакові правила в різних документах. Посилайся на канонічне джерело.

Після зміни вимог, предметної моделі, алгоритму або архітектури перевір, чи потрібно оновити відповідний документ у `docs/`.

`docs/STATUS.md` не є історичним журналом: застарілі значення замінюються актуальними. `docs/DECISIONS.md` не дублює поточні правила, а пояснює, чому були прийняті суттєві рішення.

## 9. Академічна доброчесність

- Не вигадуй факти, джерела, DOI, результати тестування або вимірювання.
- Не створюй фіктивні benchmark-результати.
- Не формулюй глобальні твердження про відсутність аналогів без доказів.
- Не допомагай приховувати використання AI.
- Код і документація, створені AI, мають залишатися зрозумілими користувачу, який несе відповідальність за фінальну роботу.

## 10. Публічний репозиторій

Репозиторій публічний.

Ніколи не commit:

- паролі;
- API keys або tokens;
- `.env` із секретами;
- приватне листування;
- зайві персональні ідентифікатори;
- конфіденційні дані.

## 11. Формат завдань

Кожне суттєве завдання бажано задавати так:

```text
Role: Developer | Reviewer
Task: <ID і назва>

Goal:
...

Read first:
- AGENTS.md
- docs/STATUS.md
- relevant docs/...
- active plan/spec

Acceptance criteria:
- ...

Tests:
- ...

Out of scope:
- ...
```

Project-wide правила з цього файлу не потрібно дублювати в кожному task prompt.

## 12. Multi-agent synchronization protocol

GitHub-репозиторій є спільним джерелом контексту між ChatGPT, Claude Code, Codex, GitHub Copilot та іншими агентами. Не покладайся на приватну історію конкретного чату як на source of truth.

### Перед початком завдання

Обов’язково прочитай у такому порядку:

1. `AGENTS.md`;
2. `docs/STATUS.md`;
3. активний task/plan/spec;
4. релевантні канонічні документи, на які посилається task.

Перед початком переконайся, що `STATUS.md` не вказує на іншого активного Developer для того самого завдання. Одночасне редагування одного task різними агентами без явної координації не допускається.

### Якщо під час роботи виникло нове суттєве питання

Суттєвим вважається питання, відповідь на яке змінює або уточнює:

- requirement або acceptance criterion;
- domain model чи invariant;
- simulation behavior або public contract;
- architecture або scope;
- погоджений technology choice.

У такому випадку Developer:

1. не приймає рішення мовчки;
2. додає в `docs/STATUS.md` запис `Q-XXX` зі статусом `OPEN`;
3. вказує task, питання та affected docs;
4. призупиняє саме ту частину реалізації, що залежить від відповіді;
5. передає питання користувачу.

Після рішення:

1. якщо рішення суттєве — додати `D-XXX` у `docs/DECISIONS.md`;
2. оновити відповідний канонічний документ;
3. видалити resolved question із `STATUS.md` або замінити його актуальним станом;
4. лише після цього продовжити залежну реалізацію.

### Після завершення Developer task

До передачі Reviewer потрібно:

1. виконати фактичні перевірки/тести;
2. зафіксувати implementation commit;
3. оновити `docs/STATUS.md`:
   - `Current phase`;
   - `Active task`;
   - `Last completed`;
   - `Current roles`;
   - `Open questions`;
   - `Last verification` з фактичним результатом;
   - relevant implementation commit;
   - `Next action`;
4. передати task іншому агенту в ролі Reviewer, якщо це передбачено workflow.

Status update може бути окремим documentation commit після implementation commit. У `STATUS.md` вказується саме relevant implementation/review commit, а не обов’язково commit самого `STATUS.md`.

### Після Reviewer

Reviewer фіксує фактичний результат review у `STATUS.md`:

- `accepted`, або
- `changes requested` із коротким посиланням на findings/task.

Reviewer не змінює канонічні правила, щоб «підігнати» їх під реалізацію.

### Обмеження розміру контекстних файлів

- `STATUS.md` — короткий поточний snapshot, орієнтовно до 50–80 рядків; не накопичує історію.
- `DECISIONS.md` — append-only журнал лише суттєвих рішень; дрібні implementation details залишаються в Git history/code review.
- Агенти не повинні читати весь `DECISIONS.md`, щоб зрозуміти поточну поведінку: для цього існують канонічні документи.
