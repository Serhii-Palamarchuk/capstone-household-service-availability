# Алгоритм симуляції доступності

## 1. Призначення документа

Цей документ визначає детермінований алгоритм оцінювання доступності побутових сервісів у заданому `Scenario`.

Предметні сутності та структурні інваріанти описані в `docs/DOMAIN_MODEL.md`. Цей документ відповідає на питання **як із валідної предметної моделі та параметрів сценарію отримується результат симуляції**.

Документ є концептуальною специфікацією алгоритму. Він не фіксує остаточні TypeScript interfaces, API-контракт або формат постійного зберігання даних.

## 2. Позначення та вхідні дані

Позначимо:

- `H` — `Scenario.outageDurationMinutes`, тривалість сценарію відключення електроенергії;
- `T(node)` — тривалість доступності вузла в хвилинах у межах конкретного сценарію;
- `targetServiceIds` — сервіс або сервіси, для яких користувач запускає оцінювання.

Усі часові значення використовуються як невід’ємні цілі хвилини. Для `Device` та `ExternalProvider` значення доступності задається явно в `Scenario.availability`. Для `Service` воно ніколи не вводиться вручну і завжди обчислюється.

Симуляція працює лише з підграфом, досяжним від `Scenario.targetServiceIds`.

## 3. Розрахунок тривалості доступності

### 3.1. Листові вузли

Для `Device`:

```text
T(Device) = Scenario.availability[deviceId]
```

Для `ExternalProvider`:

```text
T(ExternalProvider) = Scenario.availability[providerId]
```

### 3.2. Service

Усі залежності `Service` у поточному MVP є обов’язковими. Тому тривалість доступності сервісу визначається найменшою тривалістю серед його безпосередніх залежностей:

```text
T(Service) = min(T(dependency1), ..., T(dependencyN))
```

Якщо залежністю є інший `Service`, його `T` обчислюється за тим самим правилом рекурсивно.

### 3.3. Відношення до тривалості сценарію

Розраховане `T(Service)` не обрізається значенням `H`.

Наприклад, якщо `H = 360`, а `T(Service) = 480`, у результаті зберігається `480`, а `H` використовується лише для визначення статусу.

## 4. Класифікація статусу

Для кожного розрахованого `Service` визначається один із трьох статусів:

```text
Available   якщо T >= H
Limited     якщо 0 < T < H
Unavailable якщо T = 0
```

Інших статусів у MVP немає.

## 5. Обхід графа

Для розрахунку використовується рекурсивний depth-first search (`DFS`) із memoization.

Для кожного `Service` алгоритм:

1. обчислює `T` усіх його безпосередніх залежностей;
2. визначає мінімальне значення;
3. формує `ServiceResult`;
4. кешує результат за `serviceId`;
5. повторно використовує кешований результат, якщо той самий `Service` зустрічається в іншій гілці графа.

Це дозволяє коректно працювати зі спільними підграфами без повторного обчислення одного й того самого сервісу.

Обчислюються всі `Service`, досяжні від `targetServiceIds`. Основними результатами сценарію вважаються лише сервіси, явно перелічені в `targetServiceIds`; результати вкладених сервісів зберігаються для пояснення та повторного використання.

## 6. Обмежувальні залежності

### 6.1. Коли визначається bottleneck

`limitingDependencyIds` і `causalPaths` визначаються лише для статусів `Limited` та `Unavailable`.

Для `Available`:

```text
limitingDependencyIds = []
causalPaths = []
```

Навіть якщо одна залежність має найменше `T`, вона не вважається обмежувальною в межах сценарію, якщо сервіс залишається доступним протягом усього `H`.

### 6.2. Поширення мінімуму

Для `Limited` або `Unavailable` алгоритм знаходить усі безпосередні залежності, для яких:

```text
T(dependency) = T(Service)
```

Далі:

- якщо залежність має тип `Device` або `ExternalProvider`, вона є кінцевою обмежувальною причиною;
- якщо залежність має тип `Service`, алгоритм рекурсивно переходить до його залежностей із тим самим мінімальним `T`;
- якщо однакове мінімальне значення мають кілька гілок, обробляються всі такі гілки;
- проміжні `Service` не додаються до `limitingDependencyIds`, але залишаються частиною причинного шляху.

Довільний tie-breaker не використовується.

### 6.3. Унікальність причин і шляхів

`limitingDependencyIds` містить унікальні `id` кінцевих вузлів типу `Device` або `ExternalProvider`.

Якщо до одного й того самого leaf-bottleneck веде кілька різних шляхів, його `id` у `limitingDependencyIds` присутній один раз, але в `causalPaths` зберігаються всі унікальні причинні шляхи.

Кожен `ServiceResult` є самодостатнім: його causal paths починаються від саме цього `Service`, а не обов’язково від початкового target-сервісу.

Приклад:

```text
Remote Work = 120
├─ Internet = 120
│  ├─ Router = 480
│  └─ ONT/ONU = 120
└─ Laptop = 120
```

Результат для `Remote Work`:

```text
limitingDependencyIds:
- ONT/ONU
- Laptop

causalPaths:
- Remote Work -> Internet -> ONT/ONU
- Remote Work -> Laptop
```

Результат для вкладеного `Internet` має власний шлях:

```text
Internet -> ONT/ONU
```

## 7. Валідація перед симуляцією

Симуляція запускається лише після успішної валідації. Якщо знайдено хоча б одну помилку, часткові результати не повертаються.

Валідація поділяється на структурну валідацію `Scenario` та simulation-валідацію досяжного підграфа.

### 7.1. Структурна валідація Scenario

Для всього `Scenario` перевіряється:

- `outageDurationMinutes` є додатним цілим числом;
- `targetServiceIds` не порожній;
- `targetServiceIds` не містить дублікатів;
- кожен `targetServiceId` посилається на існуючий `Service`;
- кожен ключ у `availability` посилається на існуючий `Device` або `ExternalProvider`;
- кожне значення в `availability` є невід’ємним цілим числом.

Валідні значення `availability` для вузлів, які не входять до досяжного підграфа поточного запуску, дозволені та ігноруються розрахунком.

Зайве значення `availability`, яке посилається на неіснуючий вузол або на вузол неправильного типу, є помилкою структури сценарію незалежно від того, чи потрібне воно поточним target-сервісам.

### 7.2. Simulation-валідація досяжного підграфа

Для підграфа, досяжного від `targetServiceIds`, перевіряється:

- кожен досяжний `Service` має хоча б одну залежність;
- усі `dependencyIds` досяжних сервісів посилаються на існуючі вузли;
- досяжний підграф не містить циклів;
- для кожного досяжного `Device` задано `availability`;
- для кожного досяжного `ExternalProvider` задано `availability`.

Незавершена або помилкова частина моделі, яка не досягається від поточних `targetServiceIds`, не блокує конкретний запуск симуляції.

### 7.3. Збір помилок

Валідація збирає всі виявлені помилки поточного запуску, а не зупиняється на першій.

Одна й та сама проблема дедуплікується за сутністю помилки. Для звичайних помилок ключ дедуплікації концептуально складається з:

```text
code + nodeId + field
```

Порядок `ValidationError` є детермінованим:

1. `code`;
2. `nodeId`;
3. `field`.

Сортування виконується лексикографічно за зростанням; відсутнє значення поля не повинно робити порядок залежним від обходу графа.

## 8. Виявлення циклів

Редактор моделі повинен запобігати створенню нового циклічного зв’язку. Simulation engine додатково перевіряє цикли в досяжному підграфі, оскільки не повинен покладатися лише на коректність UI або зовнішнього джерела даних.

Для помилки циклу використовується `CYCLE_DETECTED` із причинним шляхом:

```text
ValidationError
- code: CYCLE_DETECTED
- nodeId: service-a
- field: dependencyIds
- path:
  - service-a
  - service-b
  - service-c
  - service-a
- message: "Виявлено циклічну залежність."
```

Один і той самий спрямований цикл не дублюється лише через іншу точку початку обходу. Для детермінованого представлення шлях циклу канонізується: початковим елементом обирається лексикографічно найменший `serviceId` у циклі, після чого цей самий `serviceId` повторюється в кінці для явного замикання циклу.

Якщо в досяжному підграфі існує кілька різних циклів, вони повертаються як окремі `CYCLE_DETECTED` errors після дедуплікації їхніх канонічних шляхів.

## 9. Коди помилок

Мінімальний набір `ValidationError.code` для MVP:

```text
INVALID_OUTAGE_DURATION
EMPTY_TARGET_SERVICES
DUPLICATE_TARGET_SERVICE
TARGET_SERVICE_NOT_FOUND

INVALID_AVAILABILITY_NODE
INVALID_AVAILABILITY_VALUE
MISSING_AVAILABILITY

SERVICE_WITHOUT_DEPENDENCIES
DEPENDENCY_NOT_FOUND
CYCLE_DETECTED
```

Семантика:

- `INVALID_OUTAGE_DURATION` — `outageDurationMinutes` не є додатним цілим числом;
- `EMPTY_TARGET_SERVICES` — не задано жодного target-сервісу;
- `DUPLICATE_TARGET_SERVICE` — один `serviceId` повторюється в `targetServiceIds`;
- `TARGET_SERVICE_NOT_FOUND` — target посилається на відсутній або не-`Service` вузол;
- `INVALID_AVAILABILITY_NODE` — ключ `availability` посилається на відсутній вузол або вузол, що не є `Device | ExternalProvider`;
- `INVALID_AVAILABILITY_VALUE` — значення `availability` не є невід’ємним цілим числом;
- `MISSING_AVAILABILITY` — для потрібного досяжного leaf-вузла відсутнє значення `availability`;
- `SERVICE_WITHOUT_DEPENDENCIES` — досяжний `Service` не має жодної залежності;
- `DEPENDENCY_NOT_FOUND` — досяжний `Service` посилається на відсутній вузол;
- `CYCLE_DETECTED` — у досяжному підграфі виявлено циклічну залежність між сервісами.

Унікальність `id`, унікальність назв і відсутність дублікатів у `Service.dependencyIds` є інваріантами предметної моделі та мають забезпечуватися шаром редагування/створення моделі. Simulation engine не є універсальним валідатором усього сховища, але перевіряє все, що необхідно для коректного та однозначного розрахунку поточного сценарію.

## 10. Контракт результату

Результат симуляції має явні взаємовиключні стани success/failure.

### 10.1. Успішний результат

Концептуально:

```text
SimulationOutcome
- success: true
- targetResults: ServiceResult[]
- serviceResults: Map<serviceId, ServiceResult>
```

`ServiceResult`:

```text
ServiceResult
- serviceId
- availabilityDurationMinutes
- status: Available | Limited | Unavailable
- limitingDependencyIds: string[]
- causalPaths: string[][]
```

Правила:

- `targetResults` повертаються у порядку `Scenario.targetServiceIds`;
- `serviceResults` містить усі розраховані досяжні `Service`;
- порядок елементів у `serviceResults` не має семантичного значення;
- окремих `DeviceResult` або `ExternalProviderResult` у MVP немає;
- leaf-вузли використовуються як вхідні значення і як кінцеві причини в `limitingDependencyIds` та `causalPaths`.

### 10.2. Помилка валідації

Концептуально:

```text
SimulationOutcome
- success: false
- errors: ValidationError[]
```

`ValidationError`:

```text
ValidationError
- code
- nodeId? 
- field?
- path?      // використовується для CYCLE_DETECTED
- message
```

При `success: false` `targetResults` і `serviceResults` не повертаються. При `success: true` validation errors не повертаються.

## 11. Детермінізм результату

За однакової предметної моделі та однакового `Scenario` simulation engine повинен повертати однаковий результат.

Для цього:

- порядок `dependencyIds` не має семантичного значення;
- `targetResults` зберігає порядок `Scenario.targetServiceIds`;
- `limitingDependencyIds` сортується лексикографічно за стабільним `id`;
- `causalPaths` сортуються лексикографічно за послідовністю `id` вузлів;
- `ValidationError` сортуються за `code`, потім `nodeId`, потім `field`;
- цикл має канонічне представлення;
- довільні tie-breaker, випадковість та евристичний вибір однієї з рівнозначних причин не використовуються.

## 12. Read-only характер симуляції

Simulation engine не змінює:

- предметну модель;
- `Scenario`;
- `Scenario.availability`;
- порядок залежностей;
- вхідні значення.

Результат є похідним від вхідних даних конкретного запуску.

## 13. Контрольний сценарій

Вхідні дані:

```text
H = 360 min

Internet
├─ Router = 480
├─ ONT/ONU = 120
└─ Internet Provider = 4320
```

Розрахунок:

```text
T(Internet) = min(480, 120, 4320) = 120
```

Статус:

```text
0 < 120 < 360
=> Limited
```

Результат:

```text
availabilityDurationMinutes = 120
status = Limited
limitingDependencyIds = [ONT/ONU]
causalPaths = [Internet -> ONT/ONU]
```

Ці значення є контрольними тестовими даними, а не результатами реальних вимірювань.

## 14. Властивості складності та межі MVP

Для валідного досяжного DAG базовий розрахунок `T` за DFS із memoization відвідує кожен досяжний вузол і зв’язок не більше необхідного для одного розрахунку; концептуально його складність становить `O(V + E)` для досяжного підграфа, без урахування сортування вихідних колекцій і переліку причинних шляхів.

Кількість різних `causalPaths` може зростати зі збільшенням кількості рівнозначних розгалужень. У MVP штучний ліміт кількості причинних шляхів не вводиться, щоб не втрачати коректні причини. Якщо фактичне performance testing покаже проблему, обмеження або інший спосіб представлення має бути окремо обґрунтований і зафіксований як нове рішення.

Simulation engine не виконує:

- прогнозування доступності;
- розрахунок автономності батарей за W/Wh;
- роботу з optional/degraded dependencies;
- імовірнісні оцінки;
- автоматичне отримання зовнішніх даних;
- рекомендації на основі ШІ.

Ці можливості не є частиною алгоритму MVP.
