# Організація роботи з репозиторієм

## Мета

Створити єдиний спільний інженерний простір для магістерського дипломного проєкту Neoversity за спеціалізацією Software Engineering, щоб ChatGPT, Claude Code, Codex, GitHub Copilot та інші coding agents працювали з однаковими вимогами, предметною моделлю, рішеннями, поточним станом і специфікаціями завдань без дублювання контексту.

## Контекст проєкту

Робоча тема:

**Оцінювання доступності критичних побутових сервісів під час відключень електроенергії на основі моделі функціональних залежностей**

Проєкт виконується індивідуально як інженерний магістерський проєкт. Основна гіпотеза полягає в тому, що доступність побутового сервісу під час відключення електроенергії потрібно оцінювати через усі його обов’язкові функціональні залежності, а не лише через автономність окремого пристрою.

MVP має залишатися вузьким, тестованим і реалістичним для реалізації однією людиною.

## Стратегія репозиторію

Для всього дипломного проєкту використовується один репозиторій.

Планована структура:

```text
/
├─ AGENTS.md
├─ CLAUDE.md
├─ .github/
│  └─ copilot-instructions.md
├─ README.md
├─ docs/
│  ├─ STATUS.md
│  ├─ PROJECT.md
│  ├─ DOMAIN_MODEL.md
│  ├─ SIMULATION.md
│  ├─ TEST_SCENARIOS.md
│  ├─ DECISIONS.md
│  ├─ specs/
│  └─ plans/
├─ apps/
│  ├─ web/
│  └─ api/              # опційно, лише якщо пізніше буде обґрунтовано
└─ .gitignore
```

Структура репозиторію має залишатися нейтральною щодо інструментів. Канонічна документація проєкту не повинна залежати від конкретного AI-плагіна, coding assistant або workflow-фреймворку.

Перший етап реалізації — клієнтський застосунок на React. Node.js API може бути доданий пізніше лише за наявності конкретної вимоги, яка обґрунтовує централізовану обробку або збереження даних.

## Єдине джерело інструкцій для агентів

`AGENTS.md` є канонічним спільним файлом стабільних інструкцій для всіх coding agents.

Він містить:

- мету та межі проєкту;
- документи, які потрібно прочитати перед реалізацією;
- режими Developer / Reviewer;
- правила тестування й перевірки;
- архітектурні та технологічні обмеження;
- synchronization protocol;
- заборону непомітно розширювати scope або приймати нові суттєві рішення.

Інструмент-специфічні файли не повинні дублювати `AGENTS.md`:

- `CLAUDE.md` лише направляє Claude Code до `AGENTS.md`;
- `.github/copilot-instructions.md` є коротким bridge для GitHub Copilot до `AGENTS.md`, `STATUS.md` та канонічних документів.

За жодним агентом постійно не закріплюється конкретна роль.

## Розділення контексту

Контекст проєкту навмисно розділено за призначенням.

### `docs/STATUS.md`

Короткий operational snapshot, що відповідає на питання **«де ми зараз?»**.

Містить лише актуальне:

- current phase;
- active task;
- last completed;
- current Developer / Reviewer;
- open questions;
- last factual verification;
- relevant implementation/review commit;
- next action.

`STATUS.md` не є журналом історії. Застарілі значення замінюються актуальними. Орієнтир розміру — до 50–80 рядків.

### Канонічні технічні документи

Відповідають на питання **«як система повинна працювати зараз?»**:

- `docs/PROJECT.md` — проблема, користувач, мета, MVP, scope, архітектурний етап;
- `docs/DOMAIN_MODEL.md` — предметна модель та інваріанти;
- `docs/SIMULATION.md` — алгоритм симуляції, validation, statuses, bottleneck, causal paths;
- `docs/TEST_SCENARIOS.md` — acceptance-сценарії й очікувана поведінка;
- `docs/specs/` — погоджені специфікації окремих підсистем/процесів;
- `docs/plans/` — погоджені implementation plans.

### `docs/DECISIONS.md`

Відповідає на питання **«чому ми так вирішили?»**.

Це append-only журнал лише суттєвих рішень, які впливають на:

- requirements;
- domain model;
- simulation/public contract;
- architecture;
- scope;
- погоджений technology choice.

Дрібні refactoring/implementation details не записуються сюди. Якщо рішення замінене, воно позначається `Superseded`, а не видаляється.

Агент не повинен читати весь `DECISIONS.md`, щоб зрозуміти поточну поведінку — актуальна істина завжди має бути перенесена до відповідного канонічного документа.

## Режими роботи

Кожне суттєве завдання явно призначає роль.

### Developer

Агент у режимі Developer:

- реалізує лише погоджене завдання;
- спочатку читає `AGENTS.md`, `STATUS.md`, active plan/task і релевантні канонічні документи;
- змінює лише файли, необхідні для поточного завдання;
- додає або оновлює тести відповідно до критеріїв приймання;
- виконує фактичну перевірку перед повідомленням про завершення;
- не розширює scope і не змінює архітектуру неявно;
- не приймає нові суттєві рішення без користувача.

### Reviewer

Агент у режимі Reviewer:

- читає той самий актуальний контекст;
- перевіряє реалізацію відносно task/spec, канонічних документів та acceptance criteria;
- перевіряє коректність, scope, тести, архітектуру та підтримуваність;
- розділяє findings щонайменше на `Critical`, `Major`, `Minor`;
- не створює нові вимоги під час review;
- за замовчуванням не змінює код.

Для одного завдання Developer і Reviewer за можливості мають бути різними агентами.

## Multi-agent synchronization protocol

GitHub-репозиторій є спільним каналом передачі контексту між агентами. Приватна історія конкретного чату не є source of truth.

Для запуску нової `Developer` або `Reviewer` сесії використовуються reusable prompts із `docs/specs/agent-session-prompts.md`. Вони є лише стартовими інструкціями: актуальний task, scope, commits і фактичний стан агент завжди визначає з `docs/STATUS.md`, active plan/spec та git history.

### Перед початком роботи

Агент читає в такому порядку:

```text
AGENTS.md
↓
docs/STATUS.md
↓
active task / plan / spec
↓
relevant canonical docs
```

Перед початком Developer перевіряє, що `STATUS.md` не вказує іншого активного Developer для того самого task. Одночасне редагування одного завдання різними агентами без явної координації не допускається.

### Якщо виникло питання, що потребує рішення

Якщо відповідь може змінити requirement, invariant, simulation behavior, architecture, scope або technology choice, Developer не повинен обирати варіант самостійно.

У `STATUS.md` створюється:

```text
Q-XXX — <коротка назва>
Task: <task id>
Question: <що саме невизначено>
Affected docs: <files>
Status: OPEN
```

Після цього призупиняється лише залежна від відповіді частина реалізації та питання передається користувачу.

Після погодження:

1. якщо рішення суттєве — додати `D-XXX` у `DECISIONS.md`;
2. оновити відповідний канонічний документ;
3. прибрати resolved question із поточного `STATUS.md`;
4. продовжити реалізацію вже з оновленим source of truth.

### Після Developer task

Developer:

1. запускає релевантні перевірки;
2. commit-ить реалізацію;
3. оновлює `STATUS.md` із фактичним результатом тестів/перевірки та relevant implementation commit;
4. виставляє `Next action` на Reviewer або наступний погоджений крок.

Status update може бути окремим documentation commit. У `STATUS.md` вказується relevant implementation commit, а не обов’язково SHA самого status update.

### Після Reviewer

Reviewer фіксує в `STATUS.md` фактичний результат:

- `accepted`; або
- `changes requested` із коротким посиланням на findings/task.

При `changes requested` next action повертається Developer. Reviewer не змінює канонічну документацію лише для того, щоб узгодити її з некоректною реалізацією.

## Формат специфікації завдання

Кожне завдання з реалізації має бути достатньо малим для одного незалежного циклу реалізації та рев’ю.

Рекомендована структура:

```text
Role: Developer | Reviewer
Task: <ID і назва>

Goal:
...

Read first:
- AGENTS.md
- docs/STATUS.md
- relevant docs/...
- active plan/spec

Acceptance criteria:
- ...

Tests:
- ...

Out of scope:
- ...
```

Task prompt має посилатися на канонічні документи замість повторення project-wide правил.

## Процес розробки

Базовий workflow:

**Специфікація → Developer → фактичні tests/checks → STATUS handoff → незалежний Reviewer → виправлення → acceptance → актуалізація документації**

Reviewer не повинен непомітно переписувати реалізацію. Findings повертаються поточному Developer, якщо користувач явно не змінює ролі.

## Обмеження scope

Ядро MVP залишається сфокусованим на:

1. створенні сценарію відключення;
2. моделюванні сервісів та залежностей;
3. описі `Device`, internal battery і `BackupSource` через погоджені характеристики W/Wh;
4. оцінюванні availability локальних `Device` у `Availability Estimator`;
5. ручному заданні availability потрібних `ExternalProvider`;
6. перевірці validation errors, зокрема циклічних залежностей;
7. детермінованій симуляції та класифікації стану сервісу;
8. визначенні обмежувальних залежностей і causal paths;
9. повторному запуску після зміни вхідних даних.

До ядра MVP не входять:

- детальна електрична модель, автоматична оптимізація або dynamic load scheduling;
- інтеграція із зовнішніми графіками відключень;
- інтеграції з інтернет-магазинами;
- AI-рекомендації;
- облікові записи користувачів;
- microservices, Kubernetes, CQRS, event-driven architecture або інша distributed-system complexity.

## Технологічні обмеження

Поточний погоджений напрям:

- React для першого етапу реалізації;
- Node.js може бути доданий пізніше лише після появи конкретної серверної вимоги.

Жодна БД, ORM, testing framework, cloud platform, broker або інша допоміжна технологія не вважається автоматично погодженою лише тому, що вона поширена або зручна.

## Принцип тестування

Кожне завдання має перевірятися за явно визначеними acceptance criteria.

Підтримується трасування:

`Requirement → Implementation → Test → Result`

Будь-які вимірювані результати мають походити з фактичного запуску тестів. Результати тестів або benchmarks не можна вигадувати.

## Правило для публічного репозиторію

Ніколи не додавати:

- паролі;
- API keys або tokens;
- секрети `.env`;
- приватне листування;
- непотрібні персональні ідентифікатори;
- конфіденційні дані.

Open questions у `STATUS.md` також формулюються без приватного листування або зайвих персональних даних.

## Зафіксоване правило для рівнозначних обмежувальних залежностей

Якщо дві або більше залежностей мають однакову мінімальну тривалість доступності, система повертає всі такі залежності як рівнозначні обмежувальні причини та не застосовує довільний tie-breaker.

Для вкладених `Service` деталізація доходить до кінцевих причин типу `Device` або `ExternalProvider`. Актуальний алгоритм і формат причинних шляхів визначає `docs/SIMULATION.md`.
