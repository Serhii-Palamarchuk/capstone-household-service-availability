# Проєкт

## 1. Формат і тема

Формат: індивідуальний магістерський інженерний проєкт, Master of Science in Computer Science, Software Engineering, Neoversity.

Робоча тема:

**«Оцінювання доступності критичних побутових сервісів під час відключень електроенергії на основі моделі функціональних залежностей»**.

У межах цього проєкту «критичні побутові сервіси» — це сервіси, важливі для конкретного користувача під час відключення електроенергії. Йдеться не про юридично визначені об’єкти критичної інфраструктури.

## 2. Проблема

Автономність окремого пристрою не визначає доступність сервісу в цілому, якщо сервіс залежить від інших пристроїв, сервісів або зовнішньої інфраструктури.

Приклад: доступ до Інтернету може залежати від роутера, ONT/ONU та інфраструктури провайдера. Тому резервного живлення лише для роутера недостатньо, щоб визначити фактичну тривалість доступності сервісу.

Проєкт фокусується на сервісному рівні: **який потрібний користувачеві сервіс залишиться доступним, як довго та яка залежність обмежує його роботу**.

## 3. Кінцевий користувач

Основний користувач — мешканець квартири або приватного будинку, який використовує чи планує резервне живлення та під час планових або аварійних відключень хоче визначити:

- які важливі для нього побутові сервіси залишаться доступними;
- як довго вони працюватимуть;
- яка залежність першою обмежує роботу сервісу.

Користувач не повинен мати спеціальних знань з електротехніки або системного моделювання.

## 4. Мета

Розробити вебсистему, яка за моделлю функціональних залежностей оцінює тривалість доступності вибраних побутових сервісів у заданому сценарії відключення електроенергії та визначає й пояснює залежність, що обмежує їхню роботу.

## 5. Основні завдання

1. Сформувати модель побутових сервісів та їхніх функціональних залежностей.
2. Забезпечити опис доступності пристроїв і зовнішніх залежностей під час відключення.
3. Реалізувати моделювання сценарію відключення заданої тривалості.
4. Визначати тривалість і стан доступності сервісів та поширювати недоступність через ланцюг залежностей.
5. Визначати обмежувальну залежність (`bottleneck`) та формувати зрозумілий причинний шлях до неї.

## 6. Gap і позиціонування новизни

Серед проаналізованих побутових рішень не виявлено публічно описаної функціональності, яка одночасно поєднує:

- явне багаторівневе моделювання залежностей сервісу;
- часову симуляцію для заданого відключення;
- причинне пояснення залежності, що обмежує доступність сервісу.

Не слід стверджувати, що прямого аналога не існує взагалі. Коректне формулювання — **«серед проаналізованих рішень»**.

Новизна проєкту не полягає у створенні нового наукового методу. Вона позиціонується як спрощена адаптація відомого моделювання функціональних залежностей до побутового сценарію з часовою оцінкою доступності та поясненням причини обмеження.

## 7. Практична цінність

Система має допомагати користувачеві до або під час сценарію відключення оцінити не лише автономність окремого обладнання, а доступність потрібного сервісу в цілому.

Приклад: збільшення резерву живлення роутера не покращить доступність Інтернету, якщо раніше стає недоступним ONT/ONU або зовнішня інфраструктура провайдера.

## 8. MVP

Один тип події: **відключення електроенергії**.

Базові сервіси для демонстрації:

- Internet;
- Remote Work;
- Heating;
- Water Supply;
- Refrigeration.

Ядро MVP:

1. створення сценарію відключення;
2. створення, редагування та видалення сервісів;
3. створення `Device` або `External Provider` і задання тривалості їхньої доступності;
4. визначення зв’язків `Service → Service | Device | External Provider`;
5. валідація обов’язкових даних і відсутності циклів;
6. запуск симуляції;
7. розрахунок тривалості доступності сервісу;
8. класифікація стану сервісу;
9. визначення обмежувальної залежності та причинного шляху;
10. відображення результату та повторний запуск після зміни вхідних даних.

## 9. Межі MVP

До ядра MVP не входять:

- автоматичний розрахунок автономності батарей за W/Wh;
- автоматичне отримання графіків відключень;
- інтеграція з інтернет-магазинами;
- AI-рекомендації;
- облікові записи;
- складна серверна або cloud infrastructure;
- microservices;
- Kubernetes;
- CQRS;
- event-driven architecture.

Ці можливості можуть розглядатися лише як `Future Work`, якщо не з’явиться окрема погоджена вимога.

## 10. Поточна предметна модель

У MVP передбачено три типи вузлів:

- `Service`;
- `Device`;
- `External Provider`.

Правила:

- `Service` може залежати від `Service`, `Device` або `External Provider`;
- усі змодельовані залежності є обов’язковими;
- optional/degraded dependencies не входять у поточний MVP;
- цикли заборонені;
- для `Device` і `External Provider` тривалість доступності є явним параметром сценарію, а не прогнозом;
- детальні інваріанти визначаються в `docs/DOMAIN_MODEL.md`.

## 11. Поточна логіка станів

Нехай:

- `H` — тривалість сценарію відключення;
- `T` — розрахована тривалість доступності сервісу.

Стани:

- `Available`: `T >= H`;
- `Limited`: `0 < T < H`;
- `Unavailable`: `T = 0`.

Детальний алгоритм має бути зафіксований у `docs/SIMULATION.md` до реалізації ядра симуляції.

## 12. Поточний архітектурний етап

Перший етап MVP — React SPA.

На цьому етапі:

- UI відповідає за введення сценарію та відображення результатів;
- предметна модель і simulation engine відокремлюються від React-компонентів;
- симуляція виконується на стороні клієнта;
- дані можуть подаватися як об’єкти/JSON;
- backend не потрібен для перевірки основної гіпотези.

Після перевірки ядра може бути розглянутий невеликий Node.js API, насамперед якщо з’явиться конкретна вимога до централізованого збереження або обробки сценаріїв.

Backend не вважається обов’язковою частиною основної гіпотези.

## 13. Тестування та оцінювання

Тестування має перевіряти вимоги, а не просто факт наявності коду.

Передбачаються за потреби:

- unit testing simulation/domain logic;
- functional testing основних користувацьких сценаріїв;
- негативні тести для некоректних даних і циклічних залежностей;
- usability evaluation основного сценарію;
- performance measurement після появи робочого прототипу.

Конкретні числові результати фіксуються тільки після фактичного виконання тестів.

Підтримується трасування:

`Requirement → Implementation → Test → Result`.

## 14. Контрольний сценарій

Перший наскрізний сценарій — доступ до Інтернету:

```text
Internet
├─ Router
├─ ONT/ONU
└─ External Provider
```

Контрольний демонстраційний приклад:

- `H = 6 h`;
- Router = `8 h`;
- ONT/ONU = `2 h`;
- External Provider = `72 h`.

Очікуване значення:

`T(Internet) = min(8, 2, 72) = 2 h`.

Отже, стан — `Limited`, а ONT/ONU є обмежувальною залежністю для цього конкретного контрольного сценарію.

Ці числа є тестовими даними сценарію, а не результатами реальних вимірювань.

## 15. Відкрите питання

Ще не зафіксовано правило для випадку, коли дві або більше залежностей мають однакову мінімальну тривалість доступності.

Не реалізовувати довільний tie-breaker. Рішення потрібно спочатку зафіксувати в `docs/DECISIONS.md` і `docs/SIMULATION.md`.
